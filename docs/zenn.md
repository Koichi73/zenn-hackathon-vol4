# 【撮るだけマニュアル】  画面収録データからマニュアルを自動生成！

## 背景
### 「マニュアル作成、面倒ですよね？」
システム開発や社内ITの運用に関わる方であれば、一度はそうため息をついたことがあるのではないでしょうか。

2023年の調査では、マニュアル作成業務の多くを「**開発担当者（17.7%）**」や「**エンジニア（15.5%）**」が担っていることがわかりました[1]。本来であればシステムの設計やコードの執筆に注力すべき貴重な時間が、退屈な作業に奪われているのが実態です。

別の調査(2024)では、半数以上の企業がマニュアルの不十分さを認識し、その原因として作成工数の不足を挙げています[2]。

### 単なる「面倒くさい」を超えた社会課題へ
この問題は、単なる現場の愚痴にとどまらず、より大きな社会課題へと結びついています。

#### 1. IT人材不足
経済産業省の調査によると、日本のIT人材は**2030年に最大で約79万人も不足する**と予測されています[3]。このような状況下で、IT人材の限られたリソースを「マニュアル作成」というアナログな作業に消費し続ける余裕は残されていません。

#### 2. 属人化の進行
マニュアルが整備されないことで、「**あのシステムの設定は〇〇さんしか分からない**」といった属人化が組織内で加速します。こうなると、組織は変化への対応力を著しく奪われ、現場の担当者にさらなるプレッシャーをかけるという悪循環に陥ってしまいます。


## 課題
前述の社会課題の根本的な原因として、現場では大きく2つの課題が発生しています。

### 課題1: マニュアル作成に時間がかかる
シンプルに「作成工程が多すぎる」という問題です。従来のマニュアル作成は、以下のようなステップを踏む必要があります。

- 対象の画面を開き、操作しながらスクリーンショットを撮る
- 画像編集ソフトやPowerPointに貼り付け、目立つように「赤枠」や「矢印」を描画する
- 「〇〇をクリックし、××を入力する」といった説明文をテキストで書き起こす
- PDFや社内Wikiにアップロードし、体裁を整える

この一連の手順の多さが、**本来エンジニアが集中すべき開発業務の時間を奪っていきます**。

### 課題2: マニュアルが間違っている
2つ目は、苦労して作ったマニュアルがすぐに役に立たなくなるという問題です。特に近年は、社内システムにSaaSを導入する企業が増えています。SaaSは機能改善のスピードが速いため、**予告なしにUIが変わる**ということが多々あります。

また、作成者のPC環境と利用者の環境に差分があるだけでも、「マニュアルと画面が違う」という混乱を招きます。結果として、せっかく作ったマニュアルが逆に問い合わせを増やす原因になってしまうのです。

### ユーザーストーリー: 「ひとり情シス vs 変化に弱い現場」
この課題が現場でどのような悲劇を生んでいるのか、具体的な2人の人物像から見てみます。

#### 手順書作成者: 孤軍奮闘する「ひとり情シス」
- 佐藤さん（32歳・入社5年目・社内SE）
- 環境: 従業員300名の中堅商社。IT担当は実質自分を含めて2名のみ。会社が「DXだ！」と言い出し、新しいSaaSと古い自社製レガシーシステムが混在する過酷な環境。

「またUIが変わってる…。スクショ撮って、赤枠つけて、パワポに貼って更新する作業、今月でもう3回目だぞ。**本当はGoogle Cloudを使った新しいアーキテクチャの設計がしたいのに**、なんで案内ばかりしているんだ…」

#### 手順書利用者: 変化が怖い「バックオフィス担当」
- 鈴木さん（30代後半・営業事務 / 経理担当）
- 環境: 業務知識は豊富で頼れる存在だが、PCスキルは「決まった手順を決まった通りにこなす」のが精一杯。

「月末の請求処理で目が回るほど忙しいのに、マニュアルにあるはずの『承認』ボタンがない！ 画面のレイアウトもなんだか違うし、適当に押してデータが消えたらどうしよう…。怖いから、とりあえず情シスの佐藤さんに電話して画面を見てもらおう！」


## 解決策
「ひとり情シス」の佐藤さんと、「変化が怖い」鈴木さん。

この2人が抱える摩擦を解消し、生産性の高い環境を実現するために私たちが開発したのが【**撮るだけマニュアル**】です。アプローチの軸は大きく2つあります。

### 1. 録画データから手順書を自動生成
1つ目の解決策は、マニュアル作成における「面倒な作業」を**すべてAIに丸投げすること**です。
作成者（佐藤さん）は、一連の業務フローを画面録画してアップロードし、待つだけです。AIが動画を解析し、以下の作業を全自動で行います。

- 必要なシーンの画像切り抜き
- 画面内の分かりづらいボタンの強調（赤枠の追加など）
- 個人情報（マスキング）の自動保護
- 各ステップの正確な説明テキスト生成

手作業で行っていた退屈な編集作業から、作成者を完全に解放します。

:::message
**なぜ「ブラウザ拡張（DOM）」ではなく「録画データ」なのか？**

現在、マニュアル生成のアプローチには「DOMイベント解析ベース（Scribe, Tangoなど）」も存在します。DOM解析ベースは裏側のHTMLコードを取得するため、テキスト生成が正確で編集も容易というメリットがあります。しかし、大きな弱点として**ブラウザ外のネイティブアプリや、Figma等のCanvasアプリでは機能しない**という問題があります。

佐藤さんを苦しめているのは、SaaSだけでなく「自社製のレガシーアプリ」の存在です。日本の現場には、ブラウザだけでは完結しない業務がまだまだ山積みになっています。だからこそ、私たちは「**画面に映るものなら何でも手順化できる**」という汎用性を最優先し、動画をベースとしたアプローチを選択しました。
:::

### 2. 利用者からのコメント機能
2つ目の解決策は、マニュアルの誤りへのアプローチです。

- **作成者（佐藤さん）のメリット**:
現場からの報告を受けたタイミングでのみ手順書を更新すればよくなります。また、コメントの数が多い箇所は、それだけ多くの人が困っている箇所だと判断でき、**優先的に更新すべき箇所が明確になります**。

- **利用者（鈴木さん）のメリット**:
マニュアルと異なる箇所があった場合、「実際の画面と違います」と簡単に報告できます。また、他の人が残したコメントを見ることで「自分の操作ミスではなく、マニュアルが古いからなんだな」と判断でき、**心理的な安心感**を得られます。

## システムアーキテクチャ
### 全体構成
![全体構成](https://storage.googleapis.com/zenn-user-upload/a736a7c9fb2f-20260215.png)

本プロダクトは、フロントエンド（Next.js）とバックエンド（FastAPI）をCloud Run上に構築し、APIで連携するアーキテクチャを採用しています。動画や生成データの保存にはCloud StorageとFirestoreを利用し、生成AIにはGemini 3.0 Flashを採用しました。

### 動画アップロードから手順書生成までの流れ
![動画アップロードから手順書生成までの流れ](https://storage.googleapis.com/zenn-user-upload/09d6daeef416-20260215.png)

動画アップロードから手順書が生成されるまでの一連の流れは、上記のシーケンスのようになっています。具体的なアーキテクチャの工夫や実装のポイントについては、次の章で詳しく解説します。


## 実装のポイント
### Gemini 3 Flash を活用した2段階解析 (動画解析 → 画像解析)
本プロダクトのコアとなる生成AIには、**マルチモーダル処理に優れるGemini 3.0 Flash**を採用しています。今回のタスクはProモデルを必要とするほどの複雑な推論は求められないため、レスポンス速度とコスト効率を優先してFlashモデルを選択しました。

実装上の工夫として、動画からいきなり完成形の手順書を出力するのではなく、「**時系列の解析（動画）**」と「**空間の解析（画像）**」で責務を分ける2段階のアプローチを取りました。

1. **動画解析**:
動画全体をGeminiに渡し、どこで画面遷移や重要なアクションが起きたかという**手順の区切り**(タイムスタンプ)を洗い出します。

2. **画像解析**:
抽出したタイムスタンプをもとに、バックエンド（ffmpeg）で該当シーンを切り出します。これらを並列で再度Geminiに渡し、説明文やハイライト位置といった詳細な空間解析を行います。

動画のまま「全体の流れ」と「各画面の細かなUI要素」を同時に解析させようとすると、**LLMが処理すべきコンテキスト量が膨大になり、ハルシネーションの増加や処理速度の低下を招きます**。このように「時系列方向」と「空間方向」でタスクを分割することで、コンテキストの肥大化を防ぎ、高精度なマニュアル生成を実現しました。

### BackgroundTasksを活用した非同期処理 & Firestoreによるリアルタイム進捗
マニュアル生成のパイプラインは時間がかかるため、これを同期処理（HTTPリクエストを繋ぎっぱなし）で実装してしまうと、**APIのタイムアウトやUXの低下を引き起こします**。

そこで、FastAPIの `BackgroundTasks` を活用し、時間のかかる解析処理はすべてバックグラウンドに逃がす非同期設計を採用しました。これとFirestoreを組み合わせることで、以下のようなメリットを生み出しています。

- **タイムアウトの回避**
- **ブラウザを閉じても裏で処理が続く**
- **段階的なUI更新**

バックエンドは解析の進捗を随時Firestoreに書き込みます。フロントエンドはFirestoreの `onSnapshot` を利用してこの変更をリアルタイムに監視し、「**処理が完了したステップから順次画面に描画していく**」という仕組みを実現しています。これにより、ユーザーを退屈させない体験を提供しています。

### 動画の直接アップロード
ユーザーが選択した動画は、フロントエンドとバックエンドを介さず、**直接Cloud Storageにアップロードされます**。これには以下の理由があります。

- **Cloud Runのリクエストサイズ制限（32MiB）の突破**
Cloud Run（HTTP/1）は仕様上、1回のリクエストサイズ上限が32MiBに制限されています。動画データはこれを容易に超過するため、サーバー経由でアップロードしようとすると、インフラ層で `413 Payload Too Large` エラーとなってしまいます。

- **メモリ枯渇とタイムアウトの防止**
巨大な動画をバックエンドで受信すると、コンテナのメモリを大量に消費し、アップロード完了までHTTPコネクションを維持するためタイムアウトのリスクも高まります。

### 解析中のUX向上
マニュアル作成までの待ち時間を退屈にさせない工夫も施しました。

- **画像解析の並列化**
動画から抽出された複数の画像フレームは、ループで直列に処理するのではなく、**非同期で一斉に処理しています**。これにより全体の処理時間を大幅に短縮できるだけでなく、解析が終わった画像から次々に表示されていくという体験を提供しています。

- **Tips表示**
動画解析中に、アプリケーションのTipsをランダムに表示しています。

:::message
実は当初、動画解析の進捗をストリーミングで取得しようと試みました。しかし、Geminiの動画解析APIの仕様上、すべてのフレーム解析が終わらないとレスポンスを取り出せないと判明しました。技術的制約に対する現実的な解として、Tips表示へと切り替えています。
:::

### 429エラーの対応
Geminiを使う上で避けて通れないものが429エラーです。特に、長時間かつトークン量が多い動画解析では、429エラーが発生しやすくなります。この対策として、リトライ処理に加えて**429エラー発生の通知機能**も実装しました。

リトライ処理が発生するとその分時間がかかり、ユーザーは「**ローディングが長いけど、フリーズしたのかな？**」と不安になります。そこで、429エラーを検知した段階で、画面上に「アクセスが集中しています」といったトースト通知（ポップアップ）を表示させるようにしました。これにより、ユーザーは状況を正しく把握でき、システムへの不信感や離脱を防ぐことができます。

:::message
Gen AI SDK では、リクエスト時のHTTPヘッダーに `X-Vertex-AI-LLM-Request-Type: dedicated` を設定することで、429エラーを意図的に発生することができます[4]。この仕組みを活用し、テストをスムーズに行うことができました。
:::

### CI/CD
デプロイ作業を自動化するため、GitHub Actions を用いた CI/CD パイプラインを構築しました。`main` ブランチへのプッシュをトリガーに、以下のフローが自動で実行されます。

1. **Google Cloud 認証**: Service Account キーを使用して Google Cloud への権限を取得
2. **ビルド・プッシュ**: Docker イメージをビルドし、Artifact Registry へプッシュ。この際、Next.jsはビルド時に環境変数を注入する必要があるため、GitHub Actions の Secrets の値を `--build-arg` として注入
3. **デプロイ**: プッシュされた最新のイメージを Cloud Run へデプロイ

これにより、手動でのビルドやコマンドラインからのデプロイといったミスの混入しやすい作業が排除され、コードの改善から本番環境への反映までが非常にスムーズになりました。


## まとめ
「撮るだけマニュアル」は、Geminiの特性を最大限活かし、エンジニアの面倒と「IT人材不足」「属人化」という社会課題に挑戦しました。

**技術的成果:**
- Gemini 3.0 Flashを用いたマニュアルの自動生成
- コメント機能によるフィードバックループの構築
- 優れたユーザー体験の実現

**解決される課題:**
- 作成者（情シス・エンジニア）:
    - マニュアル作成の負担軽減
    - マニュアル更新タイミングの把握・優先度付け
    - 本来の業務に没頭する
- 利用者:
    - マニュアルの誤りによる操作ミスや不安の解消
