## 課題
### 課題1: マニュアル作成に時間がかかる
- 手順が多い
- 画面キャプチャを撮って、説明文を書いて、画像編集して、アップロードして、という一連の作業が面倒

### 課題2: マニュアルが間違っている
- 作成者と利用者の環境差分
- SaaSの画面変更が早く、マニュアルが古くなる

### ユーザーストーリー: 「ひとり情シス vs 変化に弱い現場」
#### 手順書作成者: 孤軍奮闘する「ひとり情シス」
- 佐藤さん（32歳・入社5年目）
- 従業員300名の中堅専門商社の社内SE（システム担当は彼含め2名のみ）
- マニュアル作成が退屈
- 会社が「DXだ！」と言い出し、新しいSaaS（経費精算や勤怠管理）と、自社製の古い在庫管理システム（レガシー）が混在している
- SaaSのUIが勝手にアップデートされるたびに、「画面が違うんですけど！」という内線電話が鳴り止まない
- 「スクショ撮って、赤枠つけて、パワポに貼って…この作業、今月で3回目だぞ。俺はGoogle Cloudの設計がしたいのに、なんで案内ばかりしてるんだ…」

#### 手順書利用者: 変化が怖い「バックオフィス担当」
- 鈴木さん（30代半ば〜後半）
- 営業事務・経理担当。業務知識は豊富だが、PCスキルは決まった操作しかできない
- 月末は請求書処理で目が回るほど忙しい
- マニュアル通りにクリックしようとしたらボタンがない

## 解決策
### 1. 録画データから手順書を自動生成
動画をアップロードして待つだけ。画像切り抜きから説明文生成、個人情報のマスクまでAIが自動で行う。

#### なぜ録画データからなのか
ブラウザDOMベースだと、アプリに対応してない。特に大手企業は独自のレガシーアプリが多く存在する。
- Scribe等のDOMイベントベースは正確だが、レガシーアプリやリモートデスクトップ、FigmaなどのCanvasアプリでは機能しないという限界があること。

- 大企業ほどレガシーシステムが残っており、佐藤さん（ひとり情シス）を本当に救うには「画面に映るものなら何でも手順化できる」動画ベースのアプローチが不可欠であったこと。

### 2. 利用者からのコメント機能
コメント機能により、利用者は実際の画面と異なる部分を簡単に報告可能。作成者は、報告を受けた後、手順書を更新する。他の利用者は、マニュアルの不備を判断でき、自身の操作ミスではないという安心感を得る。

## 実装のポイント
### Gemini 3 Flash を活用した2段階解析 (動画解析 → 画像解析)
生成AIには、マルチモーダルに強いGemini 3 Flashを採用。解析内容はProを使うほど複雑ではないため、速度を優先しFlashを採用。

録画データから手順書を生成するにあたり、いきなり全てを解析するのではなく、2段階のアプローチを採用。まず、まず動画全体から「手順の区切り（タイムスタンプ）」を洗い出し、その後に必要なフレームだけを画像として切り出して詳細解析（説明文生成・マスキング・ハイライト）を行うパイプラインを構築。

コンテキストを意識した文言(動画の時系列を解析すると同時に、各画像を詳細にみるのは時間もかかるしコンテキストも増える。)時系列方向と空間方向で責務を分けることで、精度が上がる。

### BackgroundTasksを活用した非同期処理 & Firestoreによるリアルタイム進捗
マニュアル生成のパイプラインは時間がかかるため、FastAPIのBackgroundTasksを活用。HTTPリクエストをつなぎっぱなし（同期処理）にしない。Firestoreの `onSnapshot` で進捗をリアルタイムにフロントエンドに反映させている。

- タイムアウトの回避
- ブラウザを閉じても裏で処理が続く
- 画像処理が完了したものから順次フロントエンドに反映

### 動画の直接アップロード
ユーザーが選択した動画は、フロントエンド, バックエンドを介さず、直接Cloud Storageにアップロードされる仕組みを採用しています。これには以下の明確な技術的理由があります。

- Cloud Runのリクエストサイズ制限（32MiB）の突破:
Cloud Run（HTTP/1）は仕様上、1回のリクエストサイズ上限が32MiBに制限されています。動画データはこれを容易に超過するため、フロントやバックエンドを経由させてアップロードしようとすると、インフラ層で弾かれ 413 Payload Too Large エラーとなってしまいます。直接GCSへアップロードすることで、この制約を回避しています。

- バックエンドのメモリ枯渇とタイムアウトの防止:
バックエンドで巨大な動画ファイルを受信・中継（プロキシ）すると、コンテナのメモリを大量に消費し、アップロード完了までHTTPコネクションを維持するためタイムアウトのリスクも高まります。

- リソースの最適化
「結局Cloud Storageからバックエンドに動画をダウンロードするなら同じでは？」と思われるかもしれません。しかし、直接アップロードの場合、バックエンドが重い動画データを保持するのは「ffmpegでフレーム画像を切り出す一瞬だけ」です。もしバックエンド経由でアップロードすると、動画解析という長い時間、バックエンドのリソースを無駄に占有してしまいます。

### 解析中のUX向上
マニュアル作成までの待ち時間を退屈にさせない工夫。

- 動画アップロードの進捗バー
- 動画解析中のTipsの表示
- マニュアルのスケルトン表示
- 画像解析の並列化
    - 切り出した複数の画像フレームを並列にGeminiに投げている
    - 処理時間を短縮する
    - できたものからフロントエンドに反映させる

動画解析中の進捗をストリーミングなどで取得したかったが、できなかった。おそらく、動画解析では、すべてのフレームをGeminiが解析するまで返答を取り出すことはできない。加えて、どのフレームを解析中かも取得できない。そのため、Tips表示に切り替えた。
